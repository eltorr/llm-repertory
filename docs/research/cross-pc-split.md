# Second gaming PCs buy bits, not decode speed

Every system that runs one model across Ethernet-linked machines at batch 1 splits it by layers. That includes llama.cpp RPC, prima.cpp, Petals, the original exo, and vLLM, SGLang, TensorRT-LLM and NIM when they cross nodes. A pipeline boundary moves one small vector per token. Tensor and expert parallelism need RDMA-class latency (InfiniBand, Thunderbolt 5 RDMA) and lose over TCP. For Repertory the boundary carries **40,960 bytes per token**, about **33 µs at 10 GbE line rate against a 13-17 ms decode step**, so the wire is not the constraint. The gain is that each PC caches only its own 24 layers' experts. 3.05 bpw fits entirely in two RTX 5090s. 4.05 bpw goes from about 31% to about 70% of experts resident. The 5.05 and 6.05 bpw quants (84 and 100 GB without the n-gram table) become servable with every expert in VRAM or RAM and none on NVMe. Decode stays sequential, so the second PC mostly buys quality headroom. Extrapolating this repo's VRAM-scaling matrix (an estimate), 4.05 on two PCs would reach roughly today's single-PC 3.05 speed, 5.05 roughly today's 4.05 speed, and long-prompt prefill could approach 1.7x through chunk pipelining. In measured terms the quality step is small. Mean KL divergence falls from 0.0066 at 4.05 to 0.0040 and 0.0031 at 5.05 and 6.05, against a 0.0025 noise floor, so higher bits are a hedge for long agentic traces rather than a visible upgrade. Flagship MoEs such as DeepSeek V4 Flash, GLM-5.3-Flash and Qwen3.5-397B fit on two to four PCs at 2-4 bpw, but they move two to three times the bytes per token and leave no RAM for a game. The real costs are WSL2's networking (no RDMA, unmeasured per-hop latency, host-to-WSL throughput measured as low as 1.5 Gbit/s), tying two gaming PCs' availability together, and five engine seams. The first work is measurement on the existing 5090 and a two-process prototype on one PC, before buying any network card.

## Every working Ethernet cluster splits by layers, not tensors

The datacenter engines all give the same rule: tensor parallelism inside a node, pipeline parallelism across nodes. vLLM documents TP equal to GPUs per node and PP equal to node count. It warns that when NCCL falls back to a raw TCP socket, this "is not efficient for cross-node tensor parallelism" ([vLLM](https://docs.vllm.ai/en/latest/serving/parallelism_scaling.html)). NIM uses the same layout and recommends InfiniBand or RoCE for NCCL ([NVIDIA NIM](https://docs.nvidia.com/nim/large-language-models/2.0.0/deployment/multi-node-deployment.html)). At datacenter scale, MoE serving adds expert parallelism with data-parallel attention, linked by DeepEP all-to-all kernels. Those kernels require **Hopper or newer GPUs, NVLink inside a node and an RDMA network between nodes**, and TCP Ethernet is not addressed ([DeepEP](https://github.com/deepseek-ai/DeepEP)). SGLang's large-scale EP deployment ran on 12 InfiniBand-linked nodes of 8 H100s ([LMSYS](https://lmsys.org/blog/2025-05-05-large-scale-ep/)), and TensorRT-LLM's Wide-EP kernels are tuned for GB200 multi-node NVLink ([TensorRT-LLM](https://nvidia.github.io/TensorRT-LLM/latest/features/parallel-strategy.html)). DeepSpeed-MII scales across nodes by running replicas, not by sharding one model ([DeepSpeed-MII](https://github.com/deepspeedai/deepspeed-mii)). For this exact model, vLLM's recipe notes that **pipeline parallelism is not supported with the n-gram embedding** ([vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-Flash-Next)), so no off-the-shelf datacenter engine offers the split Repertory would need.

The reason is traffic. SGLang's own model puts TP at about 4·B·S·H·L bytes, with all-reduces in every layer, and PP at B·S·H·(P−1), with point-to-point sends only at stage boundaries. That makes PP "nearly an order of magnitude less" when stages are few ([LMSYS](https://lmsys.org/blog/2026-01-15-chunked-pipeline)). The catch is batch 1. Stages run one after another, so a pipeline adds capacity but not decode speed. A vLLM maintainer put it bluntly: "It is extremely inefficient to use PP if you have only one request" ([vLLM #6826](https://github.com/vllm-project/vllm/issues/6826)). Apple's MLX team measured pipeline decode across two M5 Ultras at **19.44 tok/s against 19.69 on one machine**. TP over Thunderbolt 5 RDMA reached 33.27 tok/s ([Apple ML Research](https://machinelearning.apple.com/research/mlx-distributed-inference)). That speedup depends on RDMA. Over Ethernet, TP loses even with RDMA: llama.cpp's new `-sm tensor` mode decoded **9.61 tok/s against 23.05 for layer split** on two M3 Ultras ([llama.cpp PR #26610](https://github.com/ggml-org/llama.cpp/pull/26610)). distributed-llama, the one project built around TP over plain Ethernet, spends **16-36 ms per token on synchronization** for a 70B model ([distributed-llama #147](https://github.com/b4rtaz/distributed-llama/discussions/147)).

Consumer projects therefore settle on layer splits. They differ in how they assign layers and what they do when a node drops. llama.cpp RPC splits weights in proportion to each device's memory, speaks a custom TCP protocol with RoCEv2 negotiated when both ends support it, and sends only the hidden state across the network. Its README calls the feature "fragile and insecure" ([llama.cpp RPC](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)). The original exo ran a peer-to-peer ring where each device took layers in proportion to its memory ([exo legacy](https://raw.githubusercontent.com/exo-explore/exo/v0.0.15-alpha/README.md)). exo 1.x added MLX tensor sharding over Thunderbolt 5 RDMA, but its GPU path is still Mac-only ([exo](https://github.com/exo-explore/exo)). prima.cpp cuts layers into small windows run in several rounds per token, so each device prefetches its next window from disk while the others compute. Its Halda solver places layers with an integer program that models compute, RAM and VRAM, disk speed and link latency ([prima.cpp](https://arxiv.org/html/2504.08791v3)). Petals is the only design with real fault tolerance: when a server fails, the client replays its past inputs to a replacement so the KV cache is rebuilt ([Petals](https://arxiv.org/html/2209.01188v2)).

Two lessons from these projects carry straight into Repertory. First, **latency and hop count matter; bandwidth barely does**. Petals measured 1.71 steps/s on 1 Gbit and 1.66 on 100 Mbit, but 1.23 at 100 ms round-trip time ([Petals](https://arxiv.org/html/2209.01188v2)). Second, **implementation overhead swamps the wire**. An ideal pipeline hop costs one to two percent of a token, yet llama.cpp RPC loses far more. Qwen2.5-72B fell from 11.1 to 5.9 tok/s across a Mac and a DGX Spark on 10 GbE ([kjaiswal](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks)), and Qwen3-235B Q8 went from 20.44 to 17.22 to 15.20 tok/s on one, two and four Mac Studios ([Geerling](https://github.com/geerlingguy/beowulf-ai-cluster/issues/17)). Most of that loss is the protocol re-sending compute graphs with synchronous round trips. A community patch that caches graphs lifted a 2.5 GbE pair from 5.41 to 13.21 tok/s ([llama.cpp #29253](https://github.com/ggml-org/llama.cpp/discussions/29253)). An engine with resident graphs on each node and one asynchronous send per boundary, which is what Repertory would build, should land near the ideal.

What nobody has published is a multi-machine layer split where each machine runs its own VRAM, RAM and NVMe expert tiers. KTransformers keeps hot experts on the GPU and computes cold ones on server CPUs with AMX, all inside one box. At concurrency 1, **eight GPUs gave only 26% more than one** ([LMSYS](https://www.lmsys.org/blog/2025-10-22-KTransformers/)). The closest evidence is llama.cpp's in-box multi-GPU expert cache, measured on this exact model. With two RTX 4090s, each caching the experts of the layers it owns, decode reached **64.39 tok/s at a 95.8% hit rate**, against 34.78 tok/s on the same pair without the cache, while prompt speed fell to 0.73x. The same change halved GLM 5.3 Flash's decode when a small cache hit only 43.5% ([llama.cpp PR #30112](https://github.com/ggml-org/llama.cpp/pull/30112)). One 4090 with the cache had reached 40.7 tok/s at a 77% hit rate ([llama.cpp PR #29887](https://github.com/ggml-org/llama.cpp/pull/29887)), so the second card's cache was worth about 1.6x. Across machines, the one reported attempt to combine RPC with CPU-side experts made GLM-4.6 slower, 5 to 2 tok/s ([llama.cpp #9136](https://github.com/ggml-org/llama.cpp/discussions/9136)). prima.cpp pairs a pipeline with disk offload, but only for dense models. Repertory would be first in this space.

## Each PC caches half the experts, which buys bits more than speed

Repertory's speed is set by the share of the 480 expert picks per token that VRAM serves. On the 5090, the **30-40% of experts held in VRAM serve 91-95% of picks**. That gives 72-74 tok/s at 3.05 bpw and 60-63 tok/s at 4.05, with about 1% of picks still coming from NVMe ([VRAM-scaling report](../../research/vram-scaling-torch-2.15/REPORT.md)). The store is laid out layer-major ([pack_glm53_store.py](../../glm53-flash-offload/scripts/pack_glm53_store.py)). A PC that owns 24 of the 48 MoE layers therefore needs exactly half the routed-expert bytes, and every byte of its VRAM arena goes to those layers. At 3.05 bpw each expert is 1,843,200 B and at 4.05 it is 2,457,600 B ([sizing.py](../../engines/exl3_offload/sizing.py)). The 5.05 and 6.05 branches are consistent with 5- and 6-bit experts: their measured sizes without the n-gram table are 84.3 and 100.0 GB ([turboderp](https://huggingface.co/turboderp/Qwen3.8-Flash-Next-exl3)). Each card in a split also carries only half the fixed weights and half the KV cache, so with offload on, the arena grows from today's 17.7-18.5 GB to an estimated 20-22 GB per card. With offload off and no staging buffers, 3.05 bpw becomes **fully resident with roughly a gigabyte to spare** (an estimate), provided the Windows desktop runs on the integrated GPU. That matches the "tight fit" the in-box notes found ([multi-gpu.md](multi-gpu.md)).

| Quant | Size without n-gram table | Routed experts per PC | Est. share of each PC's experts in VRAM | Mean KLD vs BF16 | Decode today, one 5090 | Est. decode, two PCs |
|---|---|---|---|---|---|---|
| 3.05 bpw | 52.5 GB | 22.6 GB | ~100% (tight) | 0.0174 | 72-74 tok/s | ~80-85 tok/s |
| 4.05 bpw | 68.5 GB | 30.2 GB | ~70% | 0.0066 | 60-63 tok/s | ~70-75 tok/s |
| 5.05 bpw | 84.3 GB | ~37.7 GB | ~55% | 0.0040 | not offered | ~60 tok/s |
| 6.05 bpw | 100.0 GB | ~45.3 GB | ~45% | 0.0031 | not offered | ~50-55 tok/s |

The decode column is an extrapolation and should be read as one; the repo has no miss-free step measurement to anchor it. In the VRAM-scaling matrix, each percentage point of VRAM pick share is worth about 0.36 ms per token at both quants. At 4.05, going from 82% to 92% VRAM picks moved the step from 19.5 to 15.9 ms. At 3.05, going from 88% to 95% moved it from 16.0 to 13.4 ms ([VRAM-scaling report](../../research/vram-scaling-torch-2.15/REPORT.md)). Extending that line puts a miss-free step near 11.6 ms at 3.05 and 13 ms at 4.05. Removing the remaining NVMe picks helps on top of that, and they are the slowest path: on the 4090, NVMe waits alone cost 12.5 ms per token ([MaxDevv's 4090 report](https://github.com/MaxDevv/lean-qwenflash/blob/fa9a772d9aa9b94a5653a2c6880eeb97af0d2e9d/research/4090-final/REPORT.md), from lean-qwenflash). The 5.05 and 6.05 rows assume the trellis kernels slow down per extra expert bit at the same rate the 3.05-to-4.05 gap implies. The result is that **each step up in bits costs about the speed the second PC's cache wins back**: 5.05 on two PCs lands near today's 4.05 on one. Same-quant gains come to roughly 10-20%, not the 1.6x llama.cpp gained going from one 4090 to two. llama.cpp started from a 77% hit rate, while Repertory's exclusive VRAM/RAM/NVMe tiers have already captured most of what a second cache can give.

The bits buy less than the memory suggests. On turboderp's in-domain trace, mean KL divergence against BF16 falls **0.0174 → 0.0066 → 0.0040 → 0.0031** from 3.05 to 6.05 bpw, against a noise floor of about 0.0025. Perplexity sits 0.36% above BF16 at 4.05 and matches it at 5.05 ([turboderp](https://huggingface.co/turboderp/Qwen3.8-Flash-Next-exl3)). Going from 4.05 to 5.05 removes about 65% of the divergence that remains above noise, and 6.05 removes about 88%. No 8 bpw quant exists, and the dense reference charts show nothing left to gain past 6 bpw ([exllamav3](https://github.com/turboderp-org/exllamav3)). Self-calibrated quants at 3.18-3.68 bpw already match the original on GPQA-Diamond (91.4-91.9% vs 91.7%), and the plain 4.05-6.05 quants have no published task benchmarks ([turboderp](https://huggingface.co/turboderp/Qwen3.8-Flash-Next-exl3)). The case for 5.05 or 6.05 rests on unmeasured territory: long-context retrieval and multi-step tool use, where small per-token divergences compound. One study found 4-bit methods losing up to 59% on long-context tasks while 8-bit lost about 0.8%, but it tested older dense models and not EXL3 ([EMNLP 2025](https://arxiv.org/abs/2505.20276v2)). Repertory already took the big step, 3.05 to 4.05. Going higher is insurance, and it should be judged on agentic evaluations run here.

Prefill is where a split earns real speed, because long prompts are the one batch-1 workload a pipeline can overlap. Today a 100K-token prompt at 4.05 takes 18.8 s (5,312 tok/s), and a fresh server's staged prefill read about 43 GB from disk at roughly 6 GB/s ([VRAM-scaling report](../../research/vram-scaling-torch-2.15/REPORT.md)). Split across two PCs, each one stages only its own layers, from RAM rather than NVMe. While PC B runs chunk i, PC A can run chunk i+1. SGLang's bubble ratio (P−1)/(P−1+M) gives about 14% for two stages and six 16K chunks, which implies roughly **1.7x prefill and a 100K TTFT near 11 s** (an estimate). The comparable in-box results are SGLang's PP4, which cut a 128K TTFT from 48.5 to 15.5 s ([LMSYS](https://lmsys.org/blog/2026-01-15-chunked-pipeline)), and 1.64x prefill from stream-loading across two 5090s in one box ([OSDI '26](https://arxiv.org/html/2606.10493)). The boundary carries 4.1 GB in fp32 for 100K tokens: about 3.5 s at 10 GbE and 1.4 s at 25 GbE. That has to overlap with compute. Sending it as fp16 would halve it, but that is a numerics change to verify by KL.

## Flagship MoEs fit on two to four PCs, at two to three times the bytes per token

Pooling nodes like the RTX 5090 PC Repertory runs on (32 GB VRAM and 64 GB RAM each, about 15% held back for the OS, KV and runtime, n-gram and Engram tables left on disk) gives roughly 165 GB of weight budget on two nodes, 245 GB on three and 330 GB on four (estimates). Several flagships with working EXL3 support fit inside that ([exllamav3](https://github.com/turboderp-org/exllamav3)). GLM-5.3-Flash at 3.05 bpw measures 125.3 GB ([turboderp](https://huggingface.co/turboderp/GLM-5.3-Flash-exl3)). DeepSeek V4 Flash (284B total, 13B active) comes to about 146 GB at 4 bpw ([DeepSeek](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/config.json)). Qwen3.5-397B-A17B is about 151 GB at 3 bpw ([Qwen](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)). DeepSeek V4.1 Flash at 2.25 bpw is 158.6 GB excluding its Engram table ([turboderp](https://huggingface.co/turboderp/DeepSeek-V4.1-Flash-1017-exl3)). Four nodes reach GLM-5.2 at 3.04 bpw (291.5 GB), but its EXL3 implementation is marked "DO NOT USE THIS YET" ([turboderp](https://huggingface.co/turboderp/GLM-5.2-exl3)). DeepSeek V4 Pro needs 400 GB even at 2 bpw, and Kimi K3 and Qwen3.8-2.4T need 612-695 GB, so they stay out of reach at four nodes.

| Cluster | Weight budget (est.) | Fits with EXL3 support today |
|---|---|---|
| 2 PCs | ~165 GB | Qwen3.8-Flash-Next at 6.05; GLM-5.3-Flash 3.05; DeepSeek V4 Flash ~4 bpw; Qwen3.5-397B ~3 bpw; DeepSeek V4.1 Flash 2.25 (borderline) |
| 3 PCs | ~245 GB | DeepSeek V4.1 Flash ~3 bpw; Qwen3.5-397B ~4.5 bpw; GLM-5.3-Flash ~6 bpw |
| 4 PCs | ~330 GB | DeepSeek V4 Flash 8 bpw; Qwen3.5-397B ~6 bpw; GLM-5.2 3.04 (support still WIP) |

Fitting is not the same as running well, and three costs stack up. First, **active parameters set the bytes read per token**: 13B for DeepSeek V4 Flash and 17B for Qwen3.5-397B, against 6B for Qwen3.8-Flash-Next ([Qwen card](https://huggingface.co/Qwen/Qwen3.8-Flash-Next)). At equal bpw that is two to three times the expert traffic, with each card's arena covering only about a quarter of its node's experts. By that arithmetic, decode would run well under half of Qwen3.8's speed on the same hardware. Second, a node holding 80 GB of weights in 96 GB of memory has nothing left for a game, which undoes the project's founding idea that the model yields to games. Third, the offload engine is shaped around `qwen4_exp`. The store packer, catalog and sizing all assume its geometry, and the upstream B70 ring shows how geometry leaks into code: it hard-codes H = 4096 and E = 288 ([ring.py](../../glm53-flash-offload/b70tier/ring.py)). nv2's per-call pick buffer (`MAXP = 80`) is sized for "<= 8 tokens x top-10" ([nv2_shared.h](../../glm53-flash-offload/kernels/nv2/nv2_shared.h)), so top-16 or top-22 models such as Kimi K3 or Nemotron 3 Ultra would need it resized.

The quality trade is real but cuts both ways. Large MoEs hold benchmark scores at very low bits. DeepSeek V4.1 Flash at 1.68 bpw scores 90.4% on GPQA-Diamond against a 90.2% baseline ([turboderp](https://huggingface.co/turboderp/DeepSeek-V4.1-Flash-1017-exl3)), while Qwen3.8-Flash-Next at 1.66 bpw drops to 86.4% from 91.7% ([turboderp](https://huggingface.co/turboderp/Qwen3.8-Flash-Next-exl3)). A bigger model at 2.5-3 bpw could therefore out-reason Qwen3.8 at 6 bpw. Its token-level divergence, though, is an order of magnitude higher (0.04-0.19 vs 0.003-0.007), and agentic robustness at those bitrates is unmeasured. Several flagships also ship natively at about 4 bits: Kimi K3 in MXFP4 with quantization-aware training, Kimi K2.6 in INT4, gpt-oss in MXFP4 ([Kimi K3](https://huggingface.co/moonshotai/Kimi-K3); [Kimi K2.6](https://huggingface.co/moonshotai/Kimi-K2.6)). For those, more bits cannot beat the release. The sound order is Qwen3.8-Flash-Next at 5.05 or 6.05 on two PCs first. A flagship comes later, as a three-to-four-PC project that needs per-architecture store packing.

## The hop is cheap; WSL2, PCIe lanes and shared gaming set the price

On the wire, a two-PC split costs one round trip per token: the 40,960-byte stream stack goes forward and the sampled token comes back. Serialization takes 33 µs at 10 GbE and 13 µs at 25 GbE. Per-message latency is what matters. On ConnectX-5, kernel TCP measured 13.72 µs of small-message MPI latency against **1.34 µs for RoCE v2** ([Sandia](https://www.osti.gov/servlets/purl/1819250)). Untuned desktops are far worse, and CPU idle states dominate. Two DGX Sparks pinged at 0.9-1.34 ms with default C-states and 22-28 µs with them disabled. That single change lifted two-node llama.cpp decode from 49.59 to 55.49 tok/s ([NVIDIA forum](https://forums.developer.nvidia.com/t/connectx-7-nic-in-dgx-spark/350417?page=3)). At 0.1-1 ms per round trip the hop costs 0.6-7% of a 13-17 ms step. **Power management is the first network tuning knob, ahead of link speed.**

WSL2 is the largest unknown, and it decides the transport. WSL2 has no NIC passthrough. Networking runs through Hyper-V's synthetic path in NAT or mirrored mode ([Microsoft](https://learn.microsoft.com/en-us/windows/wsl/networking); [WSL #10334](https://github.com/microsoft/WSL/discussions/10334)), so RDMA verbs are unavailable inside it. A July 2026 same-machine loopback test in mirrored mode measured **Windows-to-WSL throughput at 1.50 Gbit/s on one stream** and 6.25 Gbit/s on eight, and `bind()` takes about 10 ms per socket ([WSL #40965](https://github.com/microsoft/WSL/issues/40965); [WSL #41470](https://github.com/microsoft/WSL/issues/41470)). No controlled LAN-to-WSL2 latency measurement exists. If inbound traffic really caps near 1.5 Gbit/s, a 100K-token boundary transfer would take about 22 s and erase the prefill gain, while decode's 40 KB messages would still be fine. Native Linux would unlock RoCE, but GeForce cards block GPUDirect RDMA except through experimental driver patches tested on an RTX 3090 ([mcornea](https://github.com/mcornea/geforce-gpudirect-rdma)), so every hop stages through pinned host memory anyway. Native Linux also removes the Windows gaming side that the manager exists to serve. **TCP inside WSL2 is the realistic transport**, and 25 GbE pays off only if WSL2 can carry it.

The hardware is cheap. The PCIe slot is the real cost. A switchless 10 GbE pair with two NICs and a DAC was priced at $77.99 ([TechFuelHQ](https://techfuelhq.com/networking/10gbe-home-networking-budget-2026/)). Used dual-port ConnectX-4 Lx 25 GbE cards sell for $35-60 ([eBay](https://www.ebay.com/shop/mellanox-connectx-4-lx?_nkw=mellanox+connectx+4+lx)), and passive SFP DACs cost $10-19 ([ComputingForGeeks](https://computingforgeeks.com/build-10gbe-homelab-under-400/)). Three or four PCs can daisy-chain dual-port cards, because a pipeline only talks to its neighbours. On X870E boards such as the ProArt X870E-Creator, populating the second CPU-fed slot drops the GPU to x8 ([ASUS](https://www.asus.com/us/motherboards-components/motherboards/proart/proart-x870e-creator-wifi/techspec/)). That hurts Repertory more than most engines, because its RAM-tier misses and prefill staging ride the GPU link. The NIC belongs in a chipset-fed x4 slot instead. A ConnectX-4 Lx there runs at about 31.5 Gbit/s of PCIe 3.0 bandwidth, enough for one 25G port, though it shares the chipset uplink.

Splitting the model also ties two gaming PCs together, and the model becomes only as available as the less available of them. The manager's full, lean and paused profiles react to games through each PC's own GPU ([manager docs](../manager.md); [memory_guard.py](../../engines/exl3_offload/memory_guard.py)), and in a split those decisions become cluster decisions. The split has one useful property: one PC's half of the 4.05 experts (30.2 GB) fits entirely in its own RAM. When a game claims VRAM, that PC can shrink its arena live in 0.2-0.5 s ([live-resize report](../../research/live-resize/REPORT.md)) and keep serving its layers from RAM. A game that also claims RAM pushes that half onto NVMe, and a paused PC stops both. Falling back to one PC at a different quant means a reload, and startup takes 42-66 s ([VRAM-scaling report](../../research/vram-scaling-torch-2.15/REPORT.md)). Security changes too. Today the backend listens only on loopback and requires the manager's key ([manager docs](../manager.md)). A split opens a data plane on the LAN, the kind vLLM warns "can be exploited for arbitrary code execution" ([vLLM](https://docs.vllm.ai/en/latest/serving/parallelism_scaling.html)). It should bind only to the point-to-point link, authenticate with a shared key, and fail cleanly on a version mismatch. On disk, the first PC holds its half of the store plus the n-gram table (39 GB at NG6) and the token embedding. The 5.05 and 6.05 downloads are 123.3 and 139.0 GB ([turboderp](https://huggingface.co/turboderp/Qwen3.8-Flash-Next-exl3)).

## Five seams in the codebase carry the split

A cross-PC split is in one respect simpler than the in-box option the multi-GPU notes recommended. Each PC runs its own process, so nv2's single engine per process (`static Engine* G`, the module-global `NV`) can stay as it is, along with the local pinned RAM tier, NVMe readers and guards ([nv2.py](../../glm53-flash-offload/glm53/nv2.py); [nv2_host.cpp](../../glm53-flash-offload/kernels/nv2/nv2_host.cpp)). That avoids the Portable pinned-memory registration and the per-GPU rings a same-machine split would need ([multi-gpu.md](multi-gpu.md)). What has to change falls into five seams.

The first seam is layer ownership in nv2 and the store. `Nv2.__init__` asserts that the pool starts at layer 0 and matches the store's full layer list, and expert keys are `li * E + e` with `li` relative to the pool ([nv2.py](../../glm53-flash-offload/glm53/nv2.py)). Because the store is layer-major, a PC's layers form one contiguous byte range of 22.9 GB of records at 3.05 ([pack_glm53_store.py](../../glm53-flash-offload/scripts/pack_glm53_store.py)). Either nv2 and the manifest learn a nonzero layer offset, or each PC gets its own store packed from a subset. The offset is better: a PC holding the full store can also fall back to serving alone. Layer-ahead prefetch would simply stop at each PC's last layer, which costs nothing because Repertory leaves prefetch off.

The second seam is a remote segment in exllamav3's layer-split loop. `forward_ls` and `prefill_ls` walk the modules and call `prepare_for_device` before each one, and every device move funnels through `to_device` ([model_ls.py](../../exllamav3/exllamav3/model/model_ls.py); [module.py](../../exllamav3/exllamav3/modules/module.py)). Replacing a contiguous run of modules (blocks 24-47, the final hyper-connection mixer, `lm_head`) with one proxy module would serialize the `(b, s, 4, 2560)` fp32 stream stack plus the per-forward metadata the remote layers need. The hyper-connection code already flushes deferred work before a device move and breaks its pre-weighted chain at module boundaries ([hyperconnections.py](../../exllamav3/exllamav3/modules/hyperconnections.py)). Autosplit sees almost no expert bytes, so the layer map has to be explicit. Three things are untested: whether `-gs` loads `qwen4_exp` at all, how CUDA-graph decode behaves across a boundary, and exactly which `params` fields (block tables, sequence lengths, recurrent-state indices, QSA indexer caches) must cross.

The third seam is state on the remote side. The remote worker must own its layers' KV pages, Gated DeltaNet recurrent states and their checkpoints (the default interval is 2,048 tokens), and its share of the prefix cache ([qwen4_exp.py](../../exllamav3/exllamav3/architecture/qwen4_exp.py)). It must mirror the generator's page and checkpoint operations, the way tensor parallelism already mirrors `mp_cache_page_copy` to every rank ([model_tp.py](../../exllamav3/exllamav3/model/model_tp.py)). The fourth seam is the two ends of the model. The first PC owns the embedding, the stream expansion and the PLE n-gram layer at index 1, which hashes previous tokens and so needs the token history. The last PC owns the final mixer, `lm_head` and the MTP draft head, and must send back the sampled token and any drafts.

The fifth seam is the control plane. `sizing.py` plans one card for the whole model, with a single calibrated `fixed0` that cannot yet be divided by layer ([sizing.py](../../engines/exl3_offload/sizing.py)). The manager needs a cluster policy for lean and pause. The protocol can borrow the B70 ring's vocabulary: a LOAD command, request and done sequence words, a heartbeat, a 2 s timeout and an error word ([b70-tier.md](../../glm53-flash-offload/docs/b70-tier.md)). It should run at one request per token per boundary, not one per MoE layer. Two paths should not be built. exllamav3's tensor parallelism is host-local by construction: it spawns local workers, uses shared-memory broadcast and a loopback rendezvous, and needs about 96 host round trips per token ([model_tp_backend.py](../../exllamav3/exllamav3/model/model_tp_backend.py); [multi-gpu.md](multi-gpu.md)). A B70-style expert server over Ethernet would add 48 round trips per token, about 4 ms at 10 GbE line rate before any stack latency, and it depends on a CPU lane that decodes only 3-bit experts ([nv2.py](../../glm53-flash-offload/glm53/nv2.py); [b70-tier.md](../../glm53-flash-offload/docs/b70-tier.md)).

## Measure the miss-free step before buying a network card

The plan follows from where the uncertainty sits. The two numbers that decide the payoff are unknown and cheap to get: the 5090's miss-free step time and WSL2's per-hop latency. Correctness, the riskiest engineering, can be proven on one PC with no new hardware. Network hardware comes after both.

| Step | Build | Measure | Go/no-go |
|---|---|---|---|
| 0. One 5090, today's engine | Nothing new; enable the existing profiler window | Miss-free step time, per-layer time for layers 0-23 vs 24-47, time in RAM and NVMe waits | If misses are under ~10% of the step, the split buys quality and prefill only |
| 1. Two processes, one PC | Layer offset in nv2, remote-segment proxy over loopback, remote KV and recurrent state | KL and top-1 against single-process output; hop overhead; CUDA graphs, prefix cache and checkpoints | KL at the 0.0025 noise floor |
| 2. Link bench, two PCs on a DAC | Nothing engine-side | 40 KB ping-pong p50/p99 on native Windows, WSL2 mirrored and WSL2 NAT; C-states on and off; 1 GB bulk on one and many streams into WSL2 | p99 round trip under ~0.3 ms keeps WSL2 TCP; otherwise test a Windows-side relay |
| 3. 3.05 fully resident on two PCs | Offload off, explicit layer map | Decode tok/s, 100K TTFT | Beats 72-74 tok/s |
| 4. 4.05, then 5.05/6.05, offloaded | Per-PC sizing, packer and catalog entries for 5.05/6.05 | Tok/s and VRAM/RAM/NVMe pick shares per PC | 5.05 at or above today's 4.05 speed |
| 5. Pipelined prefill, cluster policy | Chunk pipelining; lean/pause coordination | 100K TTFT; behaviour when one PC starts a game | TTFT near 11 s; no hangs when a peer goes away |

Step 0 matters most because it replaces this report's extrapolation with a measurement. The multi-GPU notes already list it as their first open question ([multi-gpu.md](multi-gpu.md)). Step 1 is the cheapest place to find out whether exllamav3's generator can run with half its layers in another process. It uses two processes sharing one 5090, each caching half the experts in half the arena. Step 2 should come before buying 25 GbE, because the one published loopback test already put single-stream WSL2 traffic well below 10 GbE. Layer balance belongs in steps 0 and 3 as well. Per-layer expert demand is uneven: MoE-CORE gives some layers 120 slots against 78 for others ([MoE-CORE](https://arxiv.org/html/2610.01950)). The first PC also carries the PLE and embedding work, so the cut should follow measured time and cache pressure, not a 24/24 count. A Halda-style solver is unnecessary for two identical PCs. It earns its place only once a weaker second machine, with a smaller card or a slower PCIe link, joins.

## Conclusion

Repertory has already harvested most of what a second GPU's cache would give: 91-95% of picks come from VRAM on one card. A second PC therefore converts into bits and prefill, not decode speed. The field's evidence and this repo's own scaling curve agree on that, and it changes the goal. The goal is not a faster 4.05. It is 5.05 or 6.05 at about today's speed, plus a much shorter wait on 100K-token prompts. That also suggests a design choice the split forces early. A split at the same quant (4.05 on both PCs, with the first PC holding the full store) could fall back to one PC by loading only the other half's dense weights when a game takes over a machine, not by restarting. A higher-quant split cannot, because its fallback is a different quant and a full reload. This is a design inference, not a tested path. The gaming-first premise favours an opportunistic cluster that splits when both PCs are idle and serves alone otherwise. Going to 6.05 is worth it only if agentic evaluations show the extra bits matter.

The decisive unknown is not 10 versus 25 GbE but how WSL2 carries a 40 KB message and a 1 GB burst between two Windows machines. No source has measured either, and RDMA is closed off by both WSL2 and GeForce. No one has published a multi-machine layer split with per-machine expert tiers, so Repertory would be first. The in-box llama.cpp result on this same model is the best predictor available, and the bounded engine work (five seams, no new collectives) makes the experiment affordable once step 0 confirms the payoff.
